# User Story Mapping, критерии приёмки и обработка ошибок

## О методологии

### User Story Mapping

**User Story** — это краткое описание функциональности с точки зрения пользователя. Формат:

> **Как** <роль>, **я хочу** <действие>, **чтобы** <результат>.

**Приоритеты:**
- **Must have** — без этого продукт не работает (MVP).
- **Should have** — важно, но можно отложить на 1–2 итерацию.
- **Nice to have** — приятное дополнение.

### Acceptance Criteria (Given-When-Then)

**Критерии приёмки** описывают, когда User Story считается выполненной. Формат:

> **Given** <условие> **When** <действие> **Then** <результат>.

### Обработка ошибок

Для каждой ключевой функции описываются **негативные сценарии** (edge cases) и **UX-решения**:
- что делать при ошибках валидации;
- что показывать при отсутствии данных;
- как обрабатывать сетевые ошибки;
- что делать при неавторизованном доступе.

## 2. Детализация User Stories с Acceptance Criteria

### US-1: Регистрация нового клиента

**Как** новый посетитель, **я хочу** зарегистрироваться в системе, **чтобы** получить доступ к онлайн-записи.

**Приоритет:** Must have.

**Критерии приёмки:**

| №      | Given (Условие)                | When (Действие)                   | Then (Результат)                                    |
|--------|--------------------------------|-----------------------------------|-----------------------------------------------------|
| AC-1.1 | Я на странице `/auth/register` | Заполняю все поля корректно       | Аккаунт создан, я попадаю в `/account`              |
| AC-1.2 | Я на странице регистрации      | Ввожу email без `@`               | Поле подсвечено красным, форма не отправлена        |
| AC-1.3 | Я на странице регистрации      | Ввожу логин, который уже занят    | Сообщение «Логин, email или телефон уже заняты»     |
| AC-1.4 | Я на странице регистрации      | Ввожу пароль короче 8 символов    | Сообщение «Пароль должен содержать 8..128 символов» |
| AC-1.5 | Я на странице регистрации      | Пароли не совпадают               | Сообщение «Пароли не совпадают»                     |
| AC-1.6 | Я на странице регистрации      | Оставляю обязательное поле пустым | Сообщение «Поле обязательно для заполнения»         |

**Критерии приёмки:**

## 3. Обработка ошибок (негативные сценарии)

### 3.1. Сводная таблица edge cases

| №   | Категория         | Ситуация | UX-решение |
|-----|-------------------|-------------------------------------------------------|------------------------------------------------------------------------|
| E-1 | Валидация         | Email без `@`, пароль < 8 символов, пустые поля       | Подсветка поля + inline-сообщение под полем                            |
| E-2 | Валидация         | Длительность услуги не кратна 15                      | Сообщение у поля + красная рамка                                       |
| E-3 | Отсутствие данных | Пустая история посещений, нет активных записей        | Плейсхолдер: «У вас пока нет записей» + кнопка «Записаться»            |
| E-4 | Сетевые ошибки    | Сервер вернул 500                                     | Toast-уведомление «Что-то пошло не так. Попробуйте позже»              |
| E-5 | Авторизация       | Неавторизованный доступ к `/admin`                    | Редирект на `/auth/login` с сохранением returnTo                       |
| E-6 | Конфликт данных   | Слот занят в момент бронирования (гонка)              | Сообщение «Слот уже занят, выберите другой» + обновление списка слотов |
| E-7 | Конфликт данных   | Дублирование email/телефона при регистрации           | Inline-сообщение «Этот email уже используется»                         |
| E-8 | Бизнес-логика     | Мастер пытается завершить запись без фактической цены | Form validation: «Укажите фактическую стоимость»                       |

### 3.2. Детализация ключевых сценариев

#### E-1. Ошибки валидации формы

**Ситуация:** пользователь вводит некорректные данные в форму регистрации.

**Где возникает:** `/auth/register`, `/admin/services`, `/admin/schedules`.

**UX-решение:**
1. Поле подсвечивается красной рамкой (`border-color: var(--danger)`).
2. Под полем появляется текст ошибки (14px, красный).
3. Форма **не отправляется** на сервер (валидация на клиенте + сервере).
4. Фокус переводится на первое невалидное поле.
5. Кнопка «Отправить» остаётся активной (можно исправить и повторить).

**Пример:**

┌─────────────────────────────────────┐
│ Email:                              │
│ ┌─────────────────────────────────┐ │
│ │ user.example.com                │ │ ← красная рамка
│ └─────────────────────────────────┘ │
│ ⚠ Некорректный email               │ ← сообщение
└─────────────────────────────────────┘


#### E-3. Пустые данные

**Ситуация:** у клиента нет активных записей или истории.

**Где возникает:** `/account`, `/account/master`, `/admin/appointments`.

**UX-решение:**
1. Показывается **плейсхолдер-блок** с иконкой и текстом.
2. Добавляется **CTA-кнопка** для действия (например, «Записаться онлайн»).
3. Не показывается пустая таблица с заголовками.

**Пример:**

┌─────────────────────────────────────┐
│         📅                          │
│   У вас пока нет записей            │
│                                     │
│   [ Записаться онлайн ]             │
└─────────────────────────────────────┘

#### E-4. Сетевые ошибки (500)

**Ситуация:** сервер вернул 500 или сеть недоступна.

**Где возникает:** любой AJAX-запрос (`public/js/app.js`).

**UX-решение:**
1. Toast-уведомление в верхней части страницы:
   > ⚠ «Что-то пошло не так. Попробуйте позже.»
2. Кнопка, которая инициировала запрос, **разблокируется** (чтобы можно было повторить).
3. В консоль пишется детальная ошибка (для разработчика).
4. Если ошибка повторяется 2-3 раза — предложение обновить страницу.

**Реализация в коде:**
```js
api('POST', '/api/appointments', data).then(
  (resp) => { /* успех */ },
  (err) => {
    notify(err.message || 'Что-то пошло не так', 'error');
    $btn.prop('disabled', false);  // разблокировать кнопку
  }
);
```
#### E-5. Неавторизованный доступ

**Ситуация:** пользователь пытается открыть защищённую страницу без авторизации.

**Где возникает:** `/account`, `/account/master`, `/admin/*`.

**UX-решение:**
1. Middleware `requireAuth` перехватывает запрос.
2. Сохраняет исходный URL в `req.session.returnTo`.
3. Редиректит на `/auth/login`.
4. После успешного входа — возвращает пользователя на исходную страницу.

**Реализация:**
```js
function requireAuth(req, res, next) {
  if (req.session && req.session.user) return next();
  if (req.session) req.session.returnTo = req.originalUrl;
  return res.redirect('/auth/login');
}
```

#### E-6. Конфликт бронирования (гонка)

**Ситуация:** два клиента одновременно бронируют один слот.

**Где возникает:** `POST /api/appointments`.

**UX-решение:**
1. На уровне БД — транзакция с `SELECT ... FOR UPDATE`.
2. Второй запрос видит, что слот `busy`, и бросает `SlotUnavailableError`.
3. Клиент видит сообщение «Слот уже занят, выберите другой».
4. Список слотов **автоматически перезагружается** (AJAX), чтобы показать актуальные.

**Реализация:**
```js
return withTransaction(async (conn) => {
  const locked = await TimeSlot.lockForUpdate(conn, chain.ids);
  if (locked.some((row) => row.status !== 'free')) {
    throw new SlotUnavailableError('Выбранные слоты уже заняты');
  }
  // ... создание записи
});
```

#### E-8. Бизнес-логика: завершение без цены

**Ситуация:** мастер нажимает «Завершить», но не ввёл фактическую стоимость.

**Где возникает:** `/account/master`, форма завершения записи.

**UX-решение:**
1. Поле ввода фактической цены с плейсхолдером `Введите стоимость`.
2. При нажатии «Завершить» без цены — **inline-ошибка** «Укажите фактическую стоимость».
3. Кнопка становится неактивной до заполнения поля.
4. Значение по умолчанию — базовая цена услуги (предзаполнено).

**Пример:**
┌────────────────────────────────────┐
│ Фактическая стоимость:             │
│ ┌────────────────────────────────┐ │
│ │ 2500                           │ │ ← предзаполнено
│ └────────────────────────────────┘ │
│ [ Завершить ]                      │
└────────────────────────────────────┘

### Обработка ошибок

Реализовано 6 категорий UX-решений:
1. **Валидация** — inline-сообщения.
2. **Пустые данные** — плейсхолдеры.
3. **Сетевые ошибки** — toast + retry.
4. **Авторизация** — редирект с returnTo.
5. **Конфликты** — транзакции + перезагрузка.
6. **Бизнес-логика** — form validation.

Все решения реализованы в коде проекта и работают в проде.
